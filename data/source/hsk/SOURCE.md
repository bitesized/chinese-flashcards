# HSK word list — source, verification, and extraction spec

Owner: **Red**. Selected and pinned under [WO-003](../../../docs/workstream/work-orders/WO-003-hsk-word-list.md),
per [DEC-017](../../../docs/project/decision-log.md). See
[data-pipeline](../../../docs/engineering/data-pipeline.md) §4 for how this file is
used by the build.

**Reminder of the shape of the deal (DEC-017):** this source is taken as a
**level tag only**. The pipeline extracts exactly one fact per word — which level
it is in — plus, where available, a Pinyin reading used **only** as a build-time
matching key to resolve homographs against CC-CEDICT, then discarded. No Hanzi,
Pinyin, English gloss, classifier, or example sentence from this source is ever
shipped. All shipped content comes from CC-CEDICT.

## 3. Cumulative vs. new-words semantics — stated explicitly

The upstream repository publishes **two** variants per level: `inclusive`
(cumulative — level *N*'s file contains every word from level 1 through *N*) and
`exclusive` (only the words newly introduced at level *N*).

**We pin `exclusive`.** `Card.levels` in the domain model (§3) is populated per
word with the level(s) it belongs to, and the expected per-level counts in
[domain-model](../../../docs/engineering/domain-model.md) §9 (150 / 150 / 300 /
600 / 1,300 / 2,500) are new-words-per-level figures, not cumulative totals. Using
`inclusive` would put nearly the whole ~5,000-word corpus into the level-6 file
and silently mis-tag thousands of words. This was confirmed by fetching both
variants: `inclusive/old/6.json` contains 4,991 words — the full corpus — while
`exclusive/old/6.json` contains exactly the 2,500 new to level 6. Sanity check:
the six `exclusive` counts sum to 4,991, and `inclusive` level 6 is also 4,991 —
internally consistent.

If a future need arises for the cumulative form (e.g. "all words up to and
including HSK 3"), it is a derived computation over the pinned `exclusive` files
(set union of levels 1..N) and does not require re-pinning a different source.

## 4. Verification against the syllabus (WO-003 step 3)

1. **HSK 2.0, not HSK 3.0.** Confirmed — the repository's own `old` vs `new`
   split is unambiguous, and the level-6 word count (2,500 new, ~5,000
   cumulative) matches HSK 2.0's six-level, ~5,000-word shape, not HSK 3.0's
   nine-band, ~11,000-word shape.
2. **Per-level counts.** Found: 150 / 147 / 298 / 598 / 1,298 / 2,500 against an
   expected 150 / 150 / 300 / 600 / 1,300 / 2,500
   ([domain-model](../../../docs/engineering/domain-model.md) §9). Deviations are
   0–2 words per level (levels 2–5 are 1–3 words short of the round figures
   quoted in secondary literature, which are themselves approximate — "~150",
   "~300" etc.). This is well inside any reasonable tolerance and shows no sign
   of truncation or conflation; a truncated file would be short by tens or
   hundreds, not by 1–3.
3. **Simplified entries.** Confirmed — every entry's headword is the
   `simplified` field; a programmatic scan of all 4,991 headwords found zero
   entries containing non-CJK characters ([DEC-010](../../../docs/project/decision-log.md)).
4. **Cumulative vs. new-words.** Stated in §3 above: we use `exclusive`
   (new-words-only per level), confirmed both by the repository's own naming and
   by the count cross-check.
5. **Spot-check against my own knowledge of the syllabus.** I checked the full
   150-word HSK 1 list, the first 40 words of HSK 3, and the first 40 words of
   HSK 6 word-for-word against the standard 2010/2012 syllabus as I know it. All
   match, in the standard pinyin-alphabetical ordering the official table uses
   (HSK 1 opens 爱, 八, 爸爸, 杯子, 北京 …; HSK 6 opens with the 呵/哎哟/挨/癌症/…
   idiom-and-formal-register band expected at that level). I found no misplaced
   word in the samples checked. I did **not** exhaustively check all 4,991
   entries against the syllabus by hand — that is not practical, and is exactly
   what the count-tolerance and downstream card-level review
   ([testing-strategy](../../../docs/engineering/testing-strategy.md) §5) exist
   to catch at the level of individual cards, not the source list.

No word in the sample checked is misassigned. Acceptance criterion 7 is
therefore **vacuous for this recommendation** — I have no correction to log
against the list itself. (This is distinct from the reading-bundling issue in
§5, which is not a level misassignment.)

## 5. Known data-quality notes for Black

These affect how the extraction should be written, not whether to use this list.

### 5.1 `ü` transcription convention differs from CC-CEDICT — must be normalised

CC-CEDICT's numbered Pinyin encodes ü as `u:` (`lu:4`, `nu:3` —
[data-pipeline](../../../docs/engineering/data-pipeline.md) §3). This source's
`numeric` field instead writes **the literal `ü` character** with the tone digit
attached (`lü4`, `nü3`), not `u:`. Capitalisation and tone digits otherwise match
CC-CEDICT's convention exactly (surname/proper-noun forms are capitalised, e.g.
`Bei3 jing1`, `Du1`).

**Required normalisation before matching:** convert both sides to the same
canonical form before comparing headword+reading as a matching key. The
simplest correct approach, consistent with the id normalisation already
specified in [domain-model](../../../docs/engineering/domain-model.md) §5
("`u:` folded to `v`"): lossily fold `ü`/`u:` to `v` on **both** the HSK list's
`numeric` field and CC-CEDICT's bracketed Pinyin before comparing, in addition to
lowercasing. Do this only for the comparison key — never for anything shipped,
since shipped `reading`/`readingNumeric` always derive from CC-CEDICT, per
DEC-017.

### 5.2 Erhua suffix is inconsistently marked in a small number of entries

I checked every erhua-suffixed headword (i.e. every headword ending 儿, excluding
儿 itself) across all six files programmatically. All but one are written
correctly and match the CC-CEDICT convention exactly, e.g. `一会儿` → `yi1 hui4
r5` (identical to the example in
[data-pipeline](../../../docs/engineering/data-pipeline.md) §3). The exception:
**纽扣儿** in `hsk-6.json` writes its final syllable as bare `er` (`niu3 kou4
er`) instead of `r5` (CC-CEDICT: `niu3 kou4 r5`). Treat a trailing `er` and a
trailing `r5` on the final syllable as equivalent when matching. If any erhua
word still fails to match after this, it should fall to the normal "unmatched
word" path ([data-pipeline](../../../docs/engineering/data-pipeline.md) §5.3),
routing it to me for a manual reading — not silently dropped.

### 5.3 A word entry's multiple readings are not all necessarily "intended" at that level — flag for review, do not auto-approve

For a polyphonic headword, this source nests **every** reading it knows for that
character under one entry (`forms[]`), including rare or unrelated senses. Example
found in `hsk-1.json`: 都 carries three forms — `dōu` ("all", the actual HSK 1
item), `dū` ("capital city"), and **`Dū`, "surname Du"**. Only the first is
plausibly part of the official 150-word HSK 1 syllabus; the other two look like
this source enriching the headword with every pronunciation CC-CEDICT-like data
knows for the character, not three distinct HSK-1-intended vocabulary items. I
saw the same pattern on 还 (`hái`/`huán`, plus a `Huán` surname form) at HSK 2.

**This is not a reason to reject the list** — the level tag (都 belongs
somewhere in HSK 1) is still correct, and per DEC-017 that is the only fact being
taken. But it means: **a reading supplied by this source list and successfully
matched to a CC-CEDICT entry must not be treated as pre-approved.** It must still
carry `review: 'unreviewed'` like any other homograph-derived card, so it is
caught by the mandatory 100 % review of HSK 1–3
([testing-strategy](../../../docs/engineering/testing-strategy.md) §5) or, at
HSK 4–6, by 100 % review of homograph groups. Please confirm the matcher does not
special-case "source supplied the reading" as a reason to skip or pre-approve
review — I could not verify this from the spec alone and it matters here. If it
currently does, that is a build behaviour that would ship 都:Du1 (surname) and
还:Huan2 (surname) as unreviewed-but-shipped HSK 1/2 cards, which I would flag on
sight in review regardless, but it is cheaper to fix upstream in the pipeline
than to catch every instance by hand.

## 6. Extraction spec for Black (WO-003 acceptance criterion 5)

Per word, per level file `hsk-{N}.json`, produce **one mapping row per
`(simplified, reading)` pair** — i.e. flatten `forms[]`:

| Column | Source | Notes |
| --- | --- | --- |
| `headword` | `simplified` | Used as-is; already Simplified per §4.3. |
| `level` | the file's `N` (`'1'`…`'6'`) | One row per form, all forms in the same entry share the same level. |
| `readingNumeric` | `forms[i].transcriptions.numeric`, then apply the `ü`→`v` (or `ü`→`u:`) fold from §5.1 | This is the matching key only; never shipped. |

**Discard everything else** in the source JSON: `radical`, `frequency`, `pos`,
`forms[].traditional`, `forms[].transcriptions.pinyin` /`wadegiles`/`bopomofo`/
`romatzyh`, `forms[].meanings`, `forms[].classifiers`. None of it is used or
shipped, per DEC-017 §2 — Hanzi, Pinyin, and English all come from CC-CEDICT
only.

A headword with N forms in the source yields N mapping rows at the same level
(e.g. 行 in `hsk-4.json` yields two rows: `(行, '4', hang2)` and
`(行, '4', xing2)`). This is deliberate, not a bug to collapse — see
[data-pipeline](../../../docs/engineering/data-pipeline.md) §5.2 rule 1: where the
source supplies a reading, match headword **and** reading. Per §5.3 above, both
resulting cards still require Red's review before shipping.
