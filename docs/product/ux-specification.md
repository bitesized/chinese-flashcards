# UX Specification

Elaborates on [CLAUDE.md](../../CLAUDE.md) §02 and §03. Owner: **White**, with Red
consulted on all typographic and linguistic rendering decisions.
Status: **Draft, awaiting owner ratification.**

---

## 1. Design principles

1. **The character is the interface.** A Hanzi glyph at large size is the most
   information-dense element on screen. It gets the space. Chrome recedes.
2. **Reveal, then grade.** Two verbs, in that order, and nothing else is required.
   Everything else is optional and can be put away.
3. **Legibility over decoration.** Any visual effect that reduces the crispness of
   a Hanzi glyph or a Pinyin diacritic is wrong, however attractive.
4. **The phone is the design target.** Design at 360 px first; the desktop layout
   is the adaptation, not the other way round.
5. **Silence by default.** No sound, no motion, no notification the user did not ask for.

## 2. Visual direction

White owns the visual language. The brief from CLAUDE.md is "unique, fast, and
responsive web design without falling into AI-generated webapp tropes."

**To avoid** — the current generic-LLM-webapp house style:

- Violet-to-indigo gradients, mesh-gradient backgrounds, animated blobs
- Glassmorphism: translucent blurred panels floating on gradients
- Uniformly large border radii on every surface
- Drop shadows applied by default to elements that are not raised
- Emoji pressed into service as iconography
- Everything centred, everything the same width, everything equally spaced
- Neon-on-near-black "dark mode by default"
- A hero section, a feature grid, and a call to action — on a study tool

**To pursue instead:**

- A restrained palette: one paper ground, one ink, one accent used sparingly to
  mark state. Colour carries meaning or it is not used.
- Hierarchy from **type scale and whitespace**, not from boxes and shadows.
- Deliberate asymmetry where it aids reading. The Hanzi need not be centred if
  optical balance argues otherwise.
- Surfaces that are flat and quiet, with a single considered exception: the card
  itself, which is the one object allowed to feel physical.
- Motion used only to explain the flip. Nothing else moves.

A visual direction is not ratified until White presents at least two distinct
options to the owner. See [OQ-6](../project/open-questions.md).

## 3. Typography

This is the highest-risk area of the front end and is subject to Red's review.

| Concern | Requirement |
| --- | --- |
| CJK font stack | Must resolve to a **Simplified Chinese** face. Order: `PingFang SC`, `Hiragino Sans GB`, `Noto Sans SC`, `Source Han Sans SC`, `Microsoft YaHei`, then generic. Never allow fallback to a Japanese face — shared codepoints render with visibly wrong glyph forms (e.g. 直, 骨, 今). |
| Language tagging | Hanzi wrapped with `lang="zh-Hans"`; this drives correct glyph selection as well as screen-reader voice (NFR-8). |
| Hanzi size | Minimum 72 px on mobile for the front-of-card headword; larger where the word is short. Complex characters at small sizes are unreadable — this is a hard floor, not a preference. |
| Pinyin font | Must contain **ü with all four tone marks**: ǖ ǘ ǚ ǜ. Many otherwise-fine Latin faces omit these and will fall back mid-word, producing visibly mismatched glyphs. Verify before adopting any face. |
| Pinyin tagging | `lang="zh-Latn-pinyin"`. |
| Web fonts | If a web font is used it must be self-hosted and subset (NFR-12). A full CJK face is several megabytes — subsetting to the ~3,000 characters the HSK decks actually use is mandatory, and this subset is generated by the data pipeline. |
| Numerals and punctuation | Use Latin punctuation in English glosses as CC-CEDICT supplies them; do not convert to full-width forms. |

## 4. Screens

### 4.1 Level Select — entry screen

The default landing screen (FR-21).

- Presents the six levels: **1, 2, 3, 4, 5, 6** (FR-20).
- Each shows its card count and its **due count** (FR-24, FR-64). The due count is
  the number that matters day to day — it is what tells the learner where the work
  is — so it is the more prominent of the two.
- Levels differ enormously in size, from ~150 cards at level 1 to ~2,500 at level
  6. The design must not imply they are comparable units of work; showing counts
  honestly is the minimum, and a proportional visual treatment is worth exploring.
- Last-used level is pre-selected (FR-25).
- Multi-select is supported (FR-23); the primary action reflects the combined due
  total, e.g. "Review 42 cards".
- One tap on a level plus one tap on the primary action starts a session. With a
  remembered level, one tap total. This is what satisfies G1.
- Where a level has cards due, the primary action starts a **review** session;
  where it has none, it offers to introduce new cards, or to free-review (FR-66).

### 4.2 Study — the card

The centre of the product.

**Front state**
- Hanzi headword, dominant (FR-1).
- Pinyin above or below the Hanzi if front-Pinyin is on (FR-10, FR-11).
- Audio control (FR-40, FR-44).
- Progress indicator (FR-34).
- Reveal affordance.

**Back state**
- Hanzi remains visible. The learner must be able to connect form to meaning; a
  back face that hides the character defeats the exercise.
- Pinyin if back-Pinyin is on (FR-11).
- English sense(s), enumerated where there is more than one (FR-5).
- Measure word, set apart, where present (FR-6).
- Audio control.
- **Grading controls** (FR-61) — see below.

**Grading**

The back face carries four controls: **Again · Hard · Good · Easy**
([scheduling](../engineering/scheduling.md) §3). Design constraints:

- **Grading is the advance action.** Choosing a grade records it and moves to the
  next card. There is no separate "next" on a scheduled card; making the learner
  grade *and* advance doubles the interaction count on the app's most repeated
  action.
- **Four targets, reachable by thumb, hard to hit by accident.** They sit in the
  lower third at mobile widths, sized well above the NFR-6 minimum, with enough
  separation that a mis-tap is unlikely — a mis-grade corrupts the schedule quietly.
- **Show the resulting interval on each control** ("Good · 4d"). This is what makes
  the scheduler legible rather than magic, and it lets a learner self-correct.
- **Keys `1` `2` `3` `4`** map to the four grades, in that order.
- **Colour is not the only signal.** Grades are distinguished by position, label,
  and interval, so the control works at 3:1 contrast and for colour-blind users.
- **No default or pre-selected grade**, and no grading from the front face — a
  grade given without recall being tested is noise in the data.

In **free review** (FR-66) the grading controls are replaced by plain previous/next
navigation, and the card is visibly marked as not counting toward scheduling.

**Interactions**

| Input | Action |
| --- | --- |
| Tap / click on card | Flip (FR-2, FR-4) |
| `Space` or `Enter` | Flip; on the back face, grade `Good` |
| `1` `2` `3` `4` | Grade Again / Hard / Good / Easy (FR-61) |
| `→` / swipe left | Next card — free review only (FR-30) |
| `←` / swipe right | Previous card — free review only (FR-31) |
| `S` | Speak (FR-40) |
| `F` / `B` | Toggle front / back Pinyin (FR-14) |
| `?` | Keyboard shortcut help |

In a scheduled session, forward navigation is grading. Backward navigation is
disabled once a card is graded: un-grading would mean rolling back scheduler state,
and a card seen again immediately is not a fair test of recall. The learner may
still return to the *previous* card's information via an undo of the last grade
only — one step, clearly labelled as undo rather than as navigation.

Swipe must not fight vertical page scroll: horizontal intent is only claimed once
horizontal travel exceeds vertical travel and passes a threshold (~24 px). The
audio control must not sit inside the swipe path in a way that makes it hard to
hit.

**Flip animation.** A 3-D flip on the Y axis, 180–250 ms, ease-out. It exists to
signal that front and back are two faces of one object. Under
`prefers-reduced-motion` it becomes an instantaneous swap with a brief opacity
cross-fade (NFR-10). The flip must never delay the content: text is present in the
DOM before the animation completes.

**Announcements.** Flipping updates a polite live region so screen-reader users
receive the revealed side. The card is a `button`-role control with an accurate
accessible name, not a bare `div` with a click handler.

### 4.3 Session End

Reached when the scheduler's queue is exhausted (FR-35, FR-67).

**When there is genuinely nothing due**, say so plainly — "Nothing due. Next review
in 6 hours." Being finished is the intended outcome of a well-scheduled day, and
presenting it as an achievement rather than an empty state is the difference
between a tool that respects the learner's time and one that manufactures busywork.

Offers, in order of prominence: introduce more new cards today (if the daily limit
was the binding constraint, and with a note that this increases tomorrow's load);
free-review this level (FR-66); choose a different level. Never loops silently.

Shows what was done: cards graded, and the distribution across the four grades.

### 4.4 Settings

Reachable in one interaction from Study (FR-52).

- New cards per day — numeric, default 10 (FR-65), with a plain note that raising
  it raises future review load
- Day start hour — default 04:00 ([scheduling](../engineering/scheduling.md) §5)
- Export progress / Import progress (FR-69) — placed prominently, not buried; this
  is the learner's only backup
- Reset progress, per level or all (FR-68) — visually separated from everything
  else, confirmation names exactly what will be lost
- Front Pinyin — on/off (default **on**, see [DEC-007](../project/decision-log.md))
- Back Pinyin — on/off (default **on**)
- Card order — shuffled / sequential (FR-33)
- Speech rate — normal / slow (FR-45)
- Autoplay on reveal — default off (FR-46)
- Theme — system / light / dark (FR-54)
- Reset to defaults (FR-53)
- About: CC-CEDICT attribution and licence (NFR-11)

### 4.5 Progress

Per-level counts of new, learning, and known cards (FR-70), and optionally a
forecast of upcoming review volume (FR-71). Kept deliberately modest: the purpose
is to let a learner see where they stand, not to gamify. No streaks, no badges, no
pressure to maintain a number — those reliably cause people to grade dishonestly to
protect a statistic, which corrupts the schedule.

### 4.6 About / Attribution

Static. Carries the CC-CEDICT attribution and CC BY-SA 4.0 notice, the HSK list
provenance, and a plain statement that no data leaves the device.

## 5. Responsive behaviour

| Viewport | Layout |
| --- | --- |
| < 480 px | Single column. Card fills the available width less a comfortable margin. Controls anchored within thumb reach at the lower third. Respects `env(safe-area-inset-*)`. |
| 480–1024 px | Same single column, card capped in width and optically centred. |
| > 1024 px | Card capped (roughly 640 px). The surrounding space stays empty. Keyboard shortcuts surfaced, since a keyboard is likely present. |

Mobile carries **no** reduced feature set (NFR-5). Where a control does not fit,
it is relocated, not removed.

Additional mobile requirements: `viewport-fit=cover` with safe-area padding;
`100dvh` rather than `100vh` so the card is not clipped by dynamic browser
chrome; no double-tap-to-zoom delay on the flip target; text remains selectable
where useful but the card surface itself suppresses selection during swipe.

## 6. Empty, loading, and error states

| State | Treatment |
| --- | --- |
| First load, decks fetching | Skeleton of the card's shape. No spinner-on-blank-page. |
| Level has no cards | Should be impossible; if it occurs, say so plainly and return to Level Select. |
| No Mandarin voice available | Audio control rendered disabled with a short explanation of why (FR-43). Never a silent no-op. |
| Offline, deck not yet cached | Explain which levels are available offline and which are not. |
| Deck failed to load | Plain message, retry action, and a route back to Level Select. |
| Nothing due in any level | The day's work is done. Show when the next review falls and offer new cards or free review — never an empty screen (FR-67). |
| Import file invalid or from a newer version | Refuse, explain why, and leave existing progress untouched. A failed import must never be a partial import. |
| Persistent storage refused by the browser | A one-time, dismissible note recommending an export, with the export control to hand (NFR-16). |

## 7. Content rendering rules

Decided with Red; enforced by the data pipeline, not by ad-hoc UI logic.

1. English glosses are shown as supplied by CC-CEDICT, with cross-reference and
   classifier annotations already stripped into their own fields by the pipeline.
   The UI does not parse dictionary syntax.
2. Where an entry carries more than six senses, the first four are shown and the
   remainder are revealed by an explicit "more" control. Long definition lists
   destroy the card layout, especially at HSK 5–6.
3. Register markers such as `(coll.)`, `(lit.)`, `(fig.)` are preserved.
4. Homographs — one written form with distinct pronunciations and meanings, such
   as 行 (xíng / háng) — are **separate cards**, each with its own Pinyin and
   senses. See [domain-model](../engineering/domain-model.md) §4.
5. Pinyin is displayed syllable-spaced as CC-CEDICT groups it, with tone
   diacritics applied (FR-12) and capitalisation preserved for proper nouns.
